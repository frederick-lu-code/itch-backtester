## How a record reaches disk

The engine builds a record struct and calls `Recorder::write`. In async mode that copies it
into a 56-byte slot and pushes the slot onto the ring: a few loads, a `memcpy` and one atomic
store. The writer thread pops slots and `fwrite`s each to the file its tag names. If the ring
is full the engine yields until there is room, and the stall is counted.

## Questions a reviewer might ask

- **Why is the ring safe without locks?** One thread writes `tail_` and one writes `head_`.
  Each publishes with a release store after writing or reading the slot, and the other reads
  with an acquire load, so a slot's contents are visible before its index is.
- **Could async recording change the output?** No: each file receives its records in push
  order. A test compares sync and async runs byte for byte.
- **What does the notebook show on the reference day?** PassiveMaker loses steadily, about
  42,000 dollars, and its markouts are negative at every horizon: it is adversely selected,
  which is what a naive quoter at the touch should expect. The engine is the deliverable, not
  the strategy.
- **Why did the queue-position chart need a caveat?** Orders with the longest queues ahead
  filled most often, the opposite of the naive expectation. The cause is a confound (orders
  joining a brand-new level are usually cancelled as the touch moves on), and the notebook now
  says so instead of asserting the textbook result.
