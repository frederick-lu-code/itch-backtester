# M7 walkthrough: sharding

## What was added

- `include/itchbt/sim/sharded.hpp`: `run_sharded`, the router and the per-shard worker.
- `Backtester::start()`, `handle()` and `finish()`, so a worker can feed an engine one message
  at a time.
- `backtest --shards N`, per-shard output under `shard-<k>/`, and loader support for it.
- `tests/integration/sharded_test.cpp` and a Python test comparing a sharded run with a
  single-threaded one.

## How it works

The calling thread is the router. It runs the ordinary parser over the mapped file with a
handler whose only job is to read each validated record's stock locate and push a pointer to
the message onto that locate's shard queue (an SPSC ring of pointers into the mapping, so no
message is copied). Messages with locate 0, the system events, go to every shard. Each worker
owns a full engine and its own recorder, and stops at a null pointer.

Traded symbols are dealt to shards round-robin in config order; with `build_all_books` on,
untraded symbols are spread by locate.

## Why results are identical per symbol

A symbol's messages all go to one shard in file order, so its book and every queue position
evolve exactly as before. Order ids are per symbol by construction. Messages a shard never
sees could only have changed the wall-clock moment a queued event was released, not the
simulation time it is released at nor this symbol's book at that time.

## What is not supported

Anything that couples symbols: a strategy that reads several symbols, and the risk limits that
span symbols (gross notional, the total-PnL loss limit, the rate limit and the reject-rate
switch). `run_sharded` refuses a config that enables any of them and names them. The shipped
`passive_maker.toml` enables all four, so it runs single-threaded only.

## Done when

- Per-symbol output identical to single-threaded: tested on synthetic streams for 2, 3, 5 and

- Scaling chart in `BENCHMARKS.md`: see the sharding section there for what was and was not

## Questions a reviewer might ask

- **Is the router the bottleneck?** It does a length check, a table lookup and a ring push per
  message, which is far cheaper than a book update, so the workers dominate until there are
  many of them. `router_waits` in `run.json` counts how often a shard's queue was full.
- **What if the file is malformed half-way?** The parser stops, the router sends every shard
  its end marker, and the error is reported. There is a test for it.
- **Why pointers and not copies in the queues?** The mapping outlives the run and is read-only,
  so a pointer is all a worker needs.
- **Why not shard by hashing the locate?** Round-robin over the configured symbols balances
  the traded symbols, which carry the work that matters; hashing could put all the liquid
  names in one shard.
