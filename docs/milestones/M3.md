## One message through the engine

`Backtester` is the parser's handler. For a message stamped `t`:

1. `begin()` releases every queued event due at or before `t`: orders and cancels reach
   `SimExchange`, order updates reach the risk gate and then the strategy, timers fire. Then
   the clock moves to `t`.
2. `book::apply()` updates the historical book and returns a `BookChange`.
3. `SimExchange::on_trade_price` and `on_reduction` use that change to advance queue positions
   and generate fills. Each resulting `OrderUpdate` is recorded and queued for delivery after
   the acknowledgement latency.
4. If the top of a traded symbol's book moved, positions are marked, the change is recorded,
   and the strategy's `on_book_update` runs; executions also reach `on_trade`.

## Done when

- Fill model unit tests pass: one test per rule in the specification, plus the edge cases
  (the execution that empties the queue does not fill; a cancel that overtakes its order).
- Determinism tests pass: two runs, and runs with and without other symbols' books, produce
  byte-identical files. Confirmed on the real day as well.
- End-to-end runs complete on the full file for all three strategies.

## Questions a reviewer might ask

- **Where exactly is determinism decided?** In the event queue's ordering (release time, then
  queue order) and in the fixed sequence of steps per message. Nothing reads a clock, nothing
  iterates a hash table in the hot path, and all arithmetic is integer.
- **Does a simulated order change the historical book?** Never. It tracks its queue position
  by watching historical orders that arrived before it leave the level.
- **How optimistic is the fill model?** See README, "Simulation limits". The largest effect is
  that liquidity is never consumed: every marketable order sees the full displayed size.
- **Why is `Context` a concrete class when the engine is a template?** The specification's
  concept names `Context&` as a plain type. Everything that does not depend on the strategy
  type lives in `EngineCore`, and `Context` is a handle onto that.
- **What stops the event queue overflowing?** It is fixed-size. New orders are refused once it
  is three-quarters full, which keeps room for the updates that orders already in flight will
  generate. A dropped event is counted and reported; in every run so far the count is zero.
- **Why does an IOC report state `pending_new` on a partial fill?** The specified table gives
  an IOC no intermediate state. The final update carries `filled` or `cancelled`.
