## How the optimised book differs

Orders: one flat array of 32-byte slots instead of a node per order. A lookup hashes the
reference, lands on a slot and usually stops there. Erasing shifts the following run back one
place, so the table never accumulates tombstones.

Levels: each side is a vector of `{key, quantity, order count}` sorted so the best level is
last. Finding a level walks back from the best; adding or removing a level near the top moves
only the few entries beyond it.

## Questions a reviewer might ask

- **Why linear probing rather than something cleverer?** The table is sized for a load factor
  of at most one half, where linear probing's runs are short and each probe is the next slot
  in the same cache line or the next one. The measured replay of a real reference trace is in
  the micro-benchmark table.
- **Why is the vector not slow for deep books?** Activity is at the top. The micro-benchmark
  shows level updates near the best costing the same at 16 levels and at 4,096.
- **How do you know the fast book is the same book?** Three independent ways: the property
  test after every message, the fingerprint over the real day, and the Python reference.
- **Is prefetching safe?** It is a hint to the CPU with no effect on program state. The parser
  only offers the next message when at least 19 bytes of it lie inside the data.
- **Why is zero allocation conditional?** Because it depends on sizing, and the test that
  proves it also proves the converse. See decision F4.
- **What would you try next?** A pooled order store indexed by slot with the hash table
  holding 4-byte indices, price-indexed arrays for the most liquid symbols, and huge pages for
  the order table. None is measured, so none is claimed.
