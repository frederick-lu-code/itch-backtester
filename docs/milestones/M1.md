# M1 walkthrough: reader, parser, itch-stats

## What was added

- `include/itchbt/util/endian.hpp`: `load_be<T>` and `load_be48`.
- `include/itchbt/itch/messages.hpp`: one trivially copyable struct per message type the engine
  uses, in host byte order.
- `include/itchbt/itch/parser.hpp`: the length table, one decoder per message, `dispatch()`
  (a `switch` on the type byte into a handler template parameter) and `parse()` (the framing
  loop with bounds, type and length checks).
- `include/itchbt/itch/reader.hpp`, `src/itch/reader.cpp`: `MappedFile` (`mmap`, `PROT_READ`,
  `MAP_PRIVATE`, `MADV_SEQUENTIAL`) and `BufferedFile` (the `read()` baseline) with
  `parse_stream()`.
- `apps/itch_stats.cpp`, `tests/fuzz/parser_fuzz.cpp`, `bench/parse_bench.cpp`,
  `scripts/sysinfo.sh`, `scripts/run_bench.sh`, `bench/render.py`.

## How a message flows

`parse()` reads the 2-byte length, checks the record fits in the remaining data, reads the type
byte, and compares the length with the specification's length for that type. Only then does
`dispatch()` decode fields, so no decoder needs its own bounds checks. The handler's `on()`
overloads are resolved at compile time and inline into the loop.

## Done when

- All message types decode in unit tests, including two from hand-computed bytes.
- `itch-stats` ran over the full reference day with no errors: 268,744,780 messages, 8,906
  symbols, 03:04:32 to 20:05:00.
- Parse-only benchmark recorded in `BENCHMARKS.md`.

## Differences from the specification

- The field offsets and lengths in the specification's section 3 all match the official Nasdaq
  document. No differences were found.
- `std::byteswap` is C++23; builtins are used instead (decision B3).

## Questions a reviewer might ask

- **Why is `read()` faster than `mmap` in the benchmark?** Measured, not yet explained. The
  mapping is created inside the timed region, so every run pays for half a million page faults
  on a private file mapping. This is the first item for the M6 optimisation log.
- **What happens on a truncated file?** `parse()` returns `Truncated` with the offset of the
  incomplete record. There is a test that cuts a stream at every byte position.
- **Can a hostile file make the parser read out of bounds?** Every record is checked against
  the end of the data before any field is read, and the length must equal the fixed length for
  its type, so decoders only ever touch bytes inside a validated record. The fuzzer runs this
  under ASan and UBSan on every push.
- **Why keep the type byte in the header struct?** It costs nothing (it sits in padding) and
  lets one struct serve both `A` and `F` while tools can still tell them apart.
